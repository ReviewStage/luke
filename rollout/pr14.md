# Luke's voice on GPT Live, designed as if from scratch

## Context

Luke's voice runs on OpenAI's Realtime API: minted client secrets, a renderer
that owns the call through `@openai/agents-realtime`, one `ask_brain` function
tool, push-to-talk commits, tool-free `response.create` turns for briefings, and
a renderer-side ledger that claims replies. OpenAI has shipped GPT Live
(`gpt-live-1`), a full-duplex voice model with a different contract, and the
developer's goal is explicit: **design Luke's voice exactly as we would if Luke
had been built on GPT Live from day one**, following the GPT Live docs, with no
accommodation of the Realtime shape. This document is that design first and a
change list second.

Sources read in full: the six GPT Live guides (`live`, `live-prompting`,
`live-conversations`, `live-delegation`, `live-migration`,
`live-partner-integrations`), the WebRTC, WebSocket, server-controls, and
cost guides, the `gpt-live-1` model page, and the `openai@7.14.0` SDK types
under `resources/live/`.

### What GPT Live fixes

- Sessions are created server-side with the project key:
  `POST /v1/live/sessions { session, transport: { type: "webrtc", sdp } }` →
  `{ session: { id }, transport: { sdp } }`. No client secrets exist. The HTTP
  request starts the session; wait for `session.started` on the `oai-events`
  data channel; never send `session.start` there. Omit `audio.format` on WebRTC.
- The voice model has no tools. It **delegates**: `session.delegation.created
  { offset_ms, delegation: { id, target: "client" } }` carries no task text; the
  app composes the request from the transcripts it kept and answers with
  `session.commentary.append` (spoken, paraphrased), `session.thinking.append`
  (quiet facts), or `session.instructions.append` (behaviour). Each append:
  `event_id`, `delegation_id: string | null` (required, nullable), plain
  `content` ≤500 tokens; acked by `session.*.appended` with `client_event_id`,
  `start_ms`, `end_ms`.
- Audio streams continuously; the model decides when to speak and handles
  interruptions and backchannels itself. No turn events, no `response.done`.
  Mic control is `session.input_audio.mute/unmute` (acked). Captions are
  `session.input_transcript.delta` / `session.output_transcript.delta` with
  `start_ms/end_ms`, appended verbatim, overlap allowed, grouped by timestamps.
- Session config: `model`, `instructions` (≤16,384 tokens, immutable, in the
  documented policy structure), `input` (≤128 developer/user/assistant text
  messages, ≤8,192 tokens; no `system`), `audio.output.voice` (default `marin`;
  no speed), `delegation: { type: "client" }`, `store` (default false),
  `client.data_channel.allowed_client_events / allowed_server_events` to
  restrict an untrusted WebRTC frontend.
- A trusted server attaches a **sideband**
  `wss://api.openai.com/v1/live/sessions/{id}/attach` with the project key and
  receives every event (including reflected PCM16 audio of both speakers) and
  may send appends and close. Graceful close: register `session.closed`, send
  `session.close`, hold everything open until `session.closed { reason,
  usage.seconds }`, 15 s timeout. Billing is $0.05/min per second of session
  time, muted or not, plus 15 s at WebRTC creation credited back; sessions have
  a duration limit (`reason: "expired"`).
- The cost guide's **ambient agent** pattern: close the voice session while
  the backend works; open a new one when the user returns or a backend event
  has news, seeded with saved context in `input`.

## The design

### 1. One voice session, opened when there is something to say or hear
There is one kind of session. It opens when the developer presses the talk key
or when Luke has a briefing and no session stands. It stays open with the
conversation, full duplex, for as long as the exchange lives; the microphone is
a mute switch on that session (`session.input_audio.unmute` on the talk key,
`mute` on the stop key; since the docs note mute never stops output, the stop
key also sends the docs' corrective `instructions.append`, "stop speaking and
wait", so stop means stop), never a per-utterance gate. A voice change in
Settings applies to the next session, since voice is immutable after startup. Idle is decided from local signals, never from missing transcript events
(the docs forbid inferring silence from them): the renderer decides locally
that its microphone has carried no speech energy, or has been muted, for five
minutes and reports that once through `voice.reportLiveActivity`; the host
closes when that report stands and it has appended nothing in the same window. Then the host stops submitting appends,
closes gracefully, and records the usage. The next open is seeded through
`input` with Luke's own Conversation record (the 20 most recent lines, in
their roles) and the current redacted roster as a developer message, per the
docs' "put context the model needs from the beginning in `input`", the whole
list held under the documented 128 messages and 8,192 estimated tokens by
dropping the oldest lines first. An
`expired` close mid-conversation reopens at once, seeded the same way. A
`connection_lost` or transport failure keeps the last usage snapshot marked
unconfirmed, discards deliveries aimed at the dead session, and reopens the
same way if the mic was live. There is no separate speak-only call: a briefing,
or a brain reply that finishes after the session closed, opens the one session
there is, muted, and speaks into it with `delegation_id: null`, since a
delegation id belongs to the session that issued it (the docs' "use a backend
completion event to start a new session and notify the user"). A delegation
still retained when its session closes is dropped with it. Always-on was considered and
rejected on the docs' own cost guidance; each such open costs the 15 s
creation charge the cost guide names.

### 2. The voice has Luke's persona; the brain is the backend
Following the docs' prompt split, Luke's persona and how he talks live in the
live `instructions`, **rewritten short** in the docs' recommended shape (a few
sentences on role, tone, pace, and frustration handling; the docs call pasting
a long prompt wholesale the classic migration mistake), composed in the
documented order: identity and style,
`Backchannel policy:` (the docs' default wording, with no blanket "never speak
while the user speaks" rule beside it, which the docs warn suppresses listening
sounds), `Interruption policy:`, `Delegation policy:` with
`Backend tools:` (Luke's brain: reads the developer's coding agents, holds the
roster, settings, issues, memory, carries out actions), `Delegate to the
backend when:`, `Do not delegate to the backend when:`, and "Delegate before
giving an answer that depends on backend work. Do not guess the result while
waiting." The brain's spoken-origin turn runs under the docs' backend preamble
("you are helping an assistant in a live voice conversation; transcripts can
contain mistakes and corrections; use the latest context and verified records;
return the relevant facts, whether the task is complete, and what comes next")
and returns facts, not sentences, bounded for appends. Every action still runs
the unchanged brain path (`admit()`, tool policy, journal).

### 3. The voice knows what is on the desk
The docs' "share UI context": the same redacted roster and projects view the
brain's standing context carries (`@sidecar/brain` `standing-context.ts`) goes
into `input` as a developer message at creation and, whenever it changes while
a session stands, as one `session.thinking.append` (delegation `null`, ≤500
tokens; unchanged views skipped, rapid changes coalesced), so "that one" and "the Nukualofa
session" resolve without a round trip. This replaces the trust rule that the
voice never sees the roster; that rule guarded a voice that could act, and this
one can only delegate.

### 4. Delegation is the brain's spoken turn
On `session.delegation.created` (target `client`) the host claims the id
(duplicates ignored) and composes the ask as the role-labelled transcript of
both speakers since the previous delegation's `offset_ms`, with the developer's
latest utterance marked as the ask. If no developer utterance has arrived yet
(a delegation can precede the sentence), the delegation is **retained** and
composed when the next input fragment lands, per the docs' "retain the notice
and invoke the adapter again"; it is never answered with a "nothing heard"
note. The host mints its own submission id and keeps the delegation-to-run map
(the docs: keep operation ids separate from delegation ids), then submits
through the same admission every ask uses (`RUN_SUBMIT`'s `submit`, origin
`SPOKEN`). Progress follows the docs' "send an update when something useful
changes, combine rapid changes": one `thinking.append` under the delegation id
when the run begins a slow step (a transcript read, a provider write), not one
per tool call. The reply streams **only after every action in the run has
settled**, so nothing is announced before it is done (the docs: "do not invent
a successful action"): the brain's final answer is appended sentence by
sentence as `commentary.append` (≤500 tokens each, each awaiting its ack or
`error` before the next). A delegation that arrives while that run is still
going **steers** it through the brain's existing steer queue (the docs' "update
the same task" rule for corrections), so one reply answers both under the
newest delegation id; a delegation after the run ended starts a new one. A
refusal or cancellation is one commentary with the standing refusal sentence. A typed ask
from the composer goes to the brain as today and is **mirrored** into the
session as a `thinking.append` summary, per the docs' typed-input rule, so the
voice knows what was asked before it speaks the answer.

### 5. Briefings, replies, and onboarding are appends
An observed conversation's `announce`, a typed ask's reply, the arrival beat,
and the calendar beat are each `commentary.append` with delegation `null` into
the standing session (opening one, muted, if none stands), so Luke phrases them
in his own voice; observed values are cut to 200 chars and stripped of
newlines. Meeting and pause holds are a small queue in the live service: held
turns are re-decided when released, as today. "Spoken" is settled on the first
`session.output_transcript.delta` after the append's `end_ms`, and unsettled
again by a moderation `error` that cuts that speech (the docs: never mark an
interrupted message delivered); the renderer's speaking indicator comes from
the remote track's playback level, not the transcript. Every send waits for
its `appended` ack or an `error` matched by `client_event_id`; an error with
no `client_event_id` is logged and never treated as success; `info` events are
recorded. The old reply grant ledger, receiver epochs, speech offers, and
settle round-trips do not exist; the host owns speech.

### 6. The record is what was said
The `TranscriptLedger` keeps every fragment with its timestamps. Grouped
developer utterances become the developer's Conversation lines; grouped Luke
utterances become Luke's. Caption rows stay revisable for late fragments per
the docs' recipe; a Conversation line is written only after the gap threshold
plus a settle margin and is then final, a known limit of a stored record. The
brain's commentary text stays in the run journal. Captions draw the same
ledger, both speakers, overlap allowed, stable row ids.

### 7. The renderer is a WebRTC peer and nothing more
The voice window builds an `RTCPeerConnection` with the preferred microphone
track (`enabled = false` until unmute), a recvonly output transceiver, and the
`oai-events` channel created before the offer; gathers ICE (≤5 s); hands the
offer to main; sets the answer. Its data channel is restricted by
`client.data_channel` to client events `[session.input_audio.mute,
session.input_audio.unmute, session.close]` and server events
`[session.started, session.closed, session.input_transcript.delta,
session.output_transcript.delta, session.input_audio.muted,
session.input_audio.unmuted, session.usage.updated, error, info]`. No secret
ever reaches it. `connect-src` becomes `'none'`.

### 8. The host owns the session through a trusted sideband
Keyed tier: the host creates the session with the developer's key and attaches
the sideband itself, **before** the SDP answer is returned to the renderer, so
no transcript precedes attachment (the docs: attach early, keep history
yourself). One owner per action: the renderer owns mute, unmute, and hang-up;
the host owns every append and the close decision.

Hosted tier: one long-running **hosted voice service** (`apps/voice-service`,
Node, deployed as a container on Fly.io or Railway) owns the whole session
lifecycle, because whoever holds the project key must hold the sideband and a
Vercel function can hold neither a socket nor a call. The desktop opens one
authenticated WebSocket to it per session (account bearer on the handshake).
Over that socket the desktop sends the SDP offer; the service verifies the
account and spends the voice quota through one internal call to the Vercel
app, creates the session at OpenAI with the build's fixed instructions and
renderer permissions, attaches the sideband, answers the SDP, and from then on
is a pipe: desktop frames to OpenAI untouched, OpenAI frames to the desktop
untouched except the two reflected-audio types, which are dropped so the
developer's voice never transits Luke's service. It keeps no conversation,
logs only status codes and byte counts, records the billed seconds from
`session.closed` once per session back to the Vercel app, and closes both ends
when either closes. The same service serves the accountless introduction
session (no sideband, introduction meter). No ticket handshake exists because
create and attach are one process. The host talks to one `LiveSideband`
either way: a direct OpenAI attach on the keyed tier, the service socket on
the hosted tier.

### 9. The introduction is a greeting
The first launch's spoken introduction is the docs' "greet before the caller
speaks" pattern, which needs the input track running from the start. So the
onboarding order changes: the takeover asks for the microphone first (the
system dialog, from the developer's own press), then an accountless service
endpoint creates a session whose `instructions` carry the introduction's role,
whose `input` carries the detected sessions' titles as one developer message
(at most eight titles, each cut to 80 characters, since this is client text
entering a prompt run on Luke's key), and whose data channel allows only the
same mute, unmute, close, and captions as any session. The voice service
holds the introduction's sideband itself and sends the greeting
`instructions.append` on `session.started`, the docs' greeting pattern from
the trusted side, so an accountless caller can open a bounded introduction
and nothing else. No backend listens, so nothing can act. The takeover ends the
session when Luke's output goes quiet after the sign-off. A developer who
refuses the microphone gets the ordinary signed-out launch, as today.

### 10. Removed outright
Client secrets and every mint; `@openai/agents-realtime`; `ask_brain`;
push-to-talk commit, VAD-null, truncate/cancel, PCM press-audio appends;
speak-only calls; the speech-offer wire, reply-grant ledger, receiver epochs;
the voice speed setting (no API); `store`/fork (off); the `echo` default
(`marin`, the API default for this model). iOS and watch stay on Realtime in
this PR (`/api/voice/remote-mint` and the Realtime contract remain, documented
as the phone's); their move is a follow-up (WebRTC via the same create endpoint
with Responses delegation and the phone's action tools).

### 11. Deliberate departures from the docs, named
- A new delegation while a run is in flight **steers** that run (the brain's
  existing steer queue) rather than starting a second one, which is the docs'
  "update the same task" rule; a delegation arriving after the run ended
  starts a new one.
- The stop key mutes the microphone **and** sends
  `instructions.append` "stop speaking and wait", the docs' way to stop output.
- The five-minute idle window and the settle margins are ours; the docs say to
  tune them against recorded conversations.
- The hosted voice service drops reflected audio; the docs describe a sideband
  that receives it. Decision: the developer's voice never transits Luke's service.
- A briefing-opened session acquires the microphone (muted) without a fresh
  user gesture, under the permission onboarding already granted; nothing is
  heard until the talk key.
- `store`, forking, recording download, Responses delegation, WebSocket
  transport, and SIP are not used. Responses delegation was considered and
  rejected: Luke's brain stays the backend.
- Verification adds a small set of synthetic scenario conversations run by
  hand before and after, standing in for the docs' recorded baselines.

### 12. Follow-ups agreed (separate PRs)
- **Speculative work from transcript fragments**: start read-only brain work
  (roster refresh, transcript reads) as the developer speaks, per the docs'
  "react to transcript fragments"; never an action.
- **Transcript guardrails**: a lightweight check over accumulated user and
  assistant transcript on the host, blocking affected actions and sending the
  docs' corrective `instructions.append`, per "apply conversation guardrails".
- **Scrolling transcript panel for captions**: the docs' full caption recipe,
  stable rows, overlap, late-fragment revision, reader-controlled scrolling.
- **iOS and watch on GPT Live**: WebRTC through the same hosted voice service,
  with Responses delegation carrying the phone's action tools (the phone has no
  brain of its own).
