18Automation agents announce their turn's end, as task agents do

Today an automation's agent ends in silence: no OS notification, no toast, no unseen dot. The notices ledger (@luke/host/agent-notices.ts) keeps only agents with a plan (onPlan), and the toast's View takes a plan id. Yet AgentPlace.planId is already nullable, and its doc mentions "the agent's own page for one with no plan", so this was started and not finished.

After: the same notification, toast and unseen dot as a task agent's. The second line names the automation, where a task agent's names its plan. View opens the agent's page.

How

  • The ledger watches the one-off agents the sidebar reads (item 9's read) as well as a plan's list.
  • The toast's View is handed an AgentPlace rather than a plan id.
  • Whoever started the agent hears it. For an automation, that's its owner, whose key the run used.

19A failed run is told

Today nothing in packages/service/src/automations reaches the Inbox or a notification. A run can fail to start (repository unreachable, creator left, a guard), or its agent can fail. Either way it's seen only if someone opens the automation's Runs panel.

After, the owner is told, through doors the window already has:

  • An agent that fails is covered by item 18: its turn-end notice reads … failed.
  • A run that fails to start gets the same OS notification and toast, in the failed tone. View opens the automation.
  • The sidebar's Automations row wears the failed mark until that automation is opened.

What others do

  • GitHub Actions: notifies whoever triggered the run, or for a schedule the user who last changed its cron line. It can be set to failed runs only. The run shows a red ✕.
  • Devin: emails the schedule's owner on failure only by default. Automations offer Always, On failure or On success.
  • Zapier: emails every error by default, with a digest option.
  • Cursor, Linear, Codex and Claude Code routines: document a failed status on the run, and no alert.
  • Inbox: no one puts a failed run in an inbox of asks.

Why not the Inbox

  • The Inbox is what agents ask of you, now carried by the task's chat. A failed run asks nothing, and an item per failure would fill it on a bad day. The run's row stays the record, and the notification is the alert (Decision 13).

21AUTOMATION_PAUSE.FAILURES: delete it

The value is declared and read (the list says Paused), but never written. The usual practice is not to auto-pause on failures:

  • GitHub Actions: disables a schedule only after 60 days with no repository activity.
  • Claude Code routines: turn off only after a broken GitHub connection has lasted 72 hours.
  • Cursor, Devin's automations, Codex and Linear: document no auto-disable.
  • Zapier is the exception. It turns a Zap off when it errors 95% of the time over more than 20 runs in 7 days, after warning the account owner.

Item 19 tells the owner about every failure, and the guards already cap runs per day and at once, so I recommend deleting the dead value. The pictures below are the alternative, if Dean wants a pause: Paused after 5 failed runs in the list, and a note with Turn on in the Runs panel.
