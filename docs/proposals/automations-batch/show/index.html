5Leaving a new automation that has input asks first

Today the only guard is the one on opening a run's agent from the Runs panel, which a new automation never has. Pressing Automations in the crumbs, a sidebar row, ⌘[ back, or ⌘K leaves at once and drops the draft. That's true for an existing automation's unsaved edit too. Escape is silently swallowed while there's unsaved input. After: every way out asks with the same dialog when something written would be lost, whether it's a new draft with input or an unsaved edit. A new draft with nothing typed still leaves silently.

How

  • The editor registers a leave guard that navigation-history.ts's go, the sidebar's opens, and ⌘K all consult. The prototype only wires the crumb, Escape, and opening a run, which is enough to show the dialog. Escape asks rather than doing nothing (Decision 4).

6The runs panel resizes and folds like the side panel

9One-off agents in the sidebar

Today an agent with no task can only be reached from its automation's Runs panel, the Inbox, or a notification. Worker 324's answer for model A: they're rows inside Tasks, grouped and filtered by the same view, not a group of their own. A separate group would bring back the kind-axis group Dean removed.

  • Group by Repository: an agent sits under its repository, or under No repository.
  • Group by Creator: it sits under whoever started it.
  • Group by None: it sits in the one run, in the chosen order.

Created by filters it, and the Archived view shows archived ones. A one-off agent's row starts with its harness mark (the tab's own) so it reads apart from a task. Its end shows who started it (an automation's clock, or a teammate's face) and its last activity, so it sorts with tasks. A press opens the agent's page.

  • The service has no read of a workspace's one-off agents yet. The build adds one, readable by the same rule as tasks.

Where this meets other work

16Special handling to watch for

  • Deleted automation: coding_agent.automation_id is set to null when its automation is deleted, so today the agent forgets where it came from. Proposal: keep the automation's name on the agent when the run starts. Then the card still says Flaky test sweep (deleted), with no Open (Decision 9).
  • Turned off, or paused by a guard: nothing special. The card opens the automation, and its hover card already says it's off.
  • Someone else's personal automation: you can read the agent but not the automation (allowedTo READ). The name is already in the prompt you can read, so the card names it. It offers no Open, and its hover card says A teammate's personal automation. It never reads the automation for you.
  • Automations experiment off: the sender is named, but there's no Open, so there's no door to a page that doesn't stand.
  • GitHub event: the sender line names the subject: Code review · #2905 ⌘K view commands, linking to the pull request. The service has to hand the run's firing to the agent page. Today only the run points at the agent.
  • Webhook: the caller's body is allowed in the run's transcript (carve-out D10). It stays inside the fold under its own sub-fold, never in the sender line or the sidebar. The secret is never anywhere.
  • Run now: the sender line reads Flaky test sweep · Run by Dean.
  • Same-agent automations: later runs already arrive as messages sent by the automation (CODING_AGENT_SENDER.AUTOMATION), drawn with the same sender line. Only the agent's first message becomes the card.
  • Nested origins: one hop only. A subagent of an automation's agent opens on Subagent task from its parent agent. The parent's own card is where the automation is named. No chains of cards.
  • Archived after success: the origin still stands. ⌘F opens folded origin bodies to match inside them (useFindOpen), and Copy transcript keeps the prompt.

17Names for automation agents

Today

Every agent is named by the title model (coder-host/title.ts), from its first message, its latest, and its last answer, over its first three turns. For an automation, the first message is the whole prompt plus the "Luke started this run…" line and any event block. Until a title lands, the row and tab show the model's name (Opus 5.5). A recurring automation's runs get similar names, told apart only by time.

What others do (from their docs, and live PRs for Copilot)

  • Cursor: when no name is given, it "auto-derives a name from the prompt". Slack agents are titled from the message that started them.
  • Devin: the API takes an optional title. Otherwise the session title is generated. A schedule has its own name, and a Past Sessions list holds its runs.
  • Codex: each scheduled run starts a new chat. Runs are told apart in a Scheduled inbox with unread dots. Titles aren't documented.
  • Copilot coding agent: the PR is titled [WIP] <short LLM title> while it works, then rewritten to a descriptive title. The issue links both ways.
  • Linear agents: a session has no title of its own. It's named by its issue.

The pattern: none of them puts the automation's name or a date in a run's title. The run is titled from its prompt or its subject, the source appears as a link or badge, and recurring runs are told apart in a list on the automation.

Recommendation

  • An event about a pull request or issue: a fixed name, no model. For example #2905 ⌘K view commands, or Review #2905 … for Code review. That's how Linear and Copilot name it, it's stable across pushes, and it matches what you search for.
  • Schedule, webhook, Run now: keep the model's name. Two changes:
    • The model reads the prompt without the boilerplate line, plus the event's subject.
    • Until it lands, the placeholder is the automation's name instead of the model's.
  • The automation itself shows as the row's face and as the origin card's sender, so the title doesn't need to carry it. The Runs panel tells recurring runs apart by time, as today.

19A failed run is told

Today nothing in packages/service/src/automations reaches the Inbox or a notification. A run can fail to start (repository unreachable, creator left, a guard), or its agent can fail. Either way it's seen only if someone opens the automation's Runs panel.

After, the owner is told, through doors the window already has:

  • An agent that fails is covered by item 18: its turn-end notice reads … failed.
  • A run that fails to start gets the same OS notification and toast, in the failed tone. View opens the automation.
  • The sidebar's Automations row wears the failed mark until that automation is opened.

What others do

  • GitHub Actions: notifies whoever triggered the run, or for a schedule the user who last changed its cron line. It can be set to failed runs only. The run shows a red ✕.
  • Devin: emails the schedule's owner on failure only by default. Automations offer Always, On failure or On success.
  • Zapier: emails every error by default, with a digest option.
  • Cursor, Linear, Codex and Claude Code routines: document a failed status on the run, and no alert.
  • Inbox: no one puts a failed run in an inbox of asks.

Why not the Inbox

  • The Inbox is what agents ask of you, now carried by the task's chat. A failed run asks nothing, and an item per failure would fill it on a bad day. The run's row stays the record, and the notification is the alert (Decision 13).

The same picture shows item 23's icons; the failed run there was fired by GitHub.

21AUTOMATION_PAUSE.FAILURES: delete it

The value is declared and read (the list says Paused), but never written. The usual practice is not to auto-pause on failures:

  • GitHub Actions: disables a schedule only after 60 days with no repository activity.
  • Claude Code routines: turn off only after a broken GitHub connection has lasted 72 hours.
  • Cursor, Devin's automations, Codex and Linear: document no auto-disable.
  • Zapier is the exception. It turns a Zap off when it errors 95% of the time over more than 20 runs in 7 days, after warning the account owner.

Item 19 tells the owner about every failure, and the guards already cap runs per day and at once, so I recommend deleting the dead value. The pictures below are the alternative, if Dean wants a pause: Paused after 5 failed runs in the list, and a note with Turn on in the Runs panel.

Tools, sandbox and keys (from the same read)

  • The same for both: the tool list, the sandbox, the GitHub App token, and the owner's keys.
  • Different on purpose: the instructions. A planless agent gets no plan or page sections, and is told "No one is watching it".
  • Automations only: the concurrency, daily cap and pause guards.
  • One gap: edit_plan and show_page refuse a planless agent by design, yet both are still offered to it. Not offering them saves a wasted call and a refusal in the transcript (Decision 17).

Decisions

  1. Item 1 heading: keep the "Sharing" title over the one Owner row (recommended), or draw the Owner row in an untitled first card.
  2. Item 1 with #2781's Start from: Sharing first, then Start from (recommended, since Dean asked for Owner first), or Start from first, because it fills the whole draft.
  3. Item 4 beyond the editor: the Automations list's Owner column uses the same pictures (recommended), or it keeps its lock and building glyphs.
  4. Item 5 Escape: Escape asks with the same dialog (recommended), or it keeps doing nothing while there's input.
  5. Item 8 look: the bordered Settings picker chip for both workspace and repository (recommended, as in the pictures), or both as the composer's quiet pill with a chevron.
  6. Item 9 leading glyph: the agent's harness mark, as its tab wears it (recommended), or one generic agent glyph for every agent.
  7. Item 12 scope: find matches the page's text, not typed field values, and Settings keeps ⌘F on its search (recommended), or find also searches inside fields and Settings gets find-in-page.
  8. Item 14 for task agents: the Plan card gets the same sender line, the person who started the agent (recommended), or it stays without a sender and only moves to message width.
  9. Item 16 deleted automation: keep the automation's name on the agent when the run starts, so a deleted one is still named (recommended; one nullable column), or the card falls back to a nameless "Automation".
  10. Item 17: fixed names for pull-request and issue events, and model names with the automation's name as placeholder for the rest (recommended); or model names for everything as today; or always <automation> · <subject or date>.
  11. Item 18 second line: the automation's name, where a task agent's names its plan (recommended), or the repository.
  12. Item 19 who is told: the automation's owner, whose key runs it (recommended), or, for a workspace automation, also its last editor or every owner and admin.
  13. Item 19 Inbox: no Inbox item; the notification, toast and Automations mark do it (recommended), or an Inbox item per failed run.
  14. Item 21: delete AUTOMATION_PAUSE.FAILURES (recommended, the common practice), or pause after 5 failed runs in a row, tell the owner, and offer Turn on in the Runs panel (pictured).
  15. Item 22: one MCP servers row reusing the composer's servers popover (recommended), or a card of per-server switch rows.
  16. Item 24: the agent page gets the plan column's side panel, so workers and Changes open there as on a task (recommended), or workers open as pages of their own.
  17. Stop offering edit_plan and show_page to agents without a plan (recommended), or keep offering them and let them refuse.
