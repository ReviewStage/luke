Images in agent output

Dean asked: “I think popular coding agents are able to display images in their output. How does that work? Can we add support for that?” This show is the proposal in docs/proposals/agent-output-images.md, drawn by main's real components with the proposal patched into their sources, over main's compiled stylesheet pinned to each appearance. The screenshots are synthetic, and the frames are the proposal as drawn before it was built. All five PRs have since shipped (#2906, #2911, #2919, #2927, #2979). “As decided and shipped” in the proposal says where they differ, chiefly that Add to plan always appends at the plan’s end, with Undo.

The proposal in one breath. An agent shows a picture by calling show_image(path, caption) on a file in its sandbox; an integration's MCP tool that answers an image has it kept the same way. The service stores the bytes once, in a conversation_attachment table beside 318's plan_attachment, and the transcript names the file by id, never by base64. The desktop reads each file by id into the window's cache and draws it with plan-media's picture, states and lightbox. A markdown image in a reply is never fetched. Add to plan copies a picture into the plan.

Found on main while mapping this. An MCP tool's image is stored today as base64 inside messages.parts, twice when the nested call is kept. It is rewritten with every journal amend of its turn, sent whole on each long-poll page, and drawn as a wall of base64 in its row. The first PR fixes that before anything is drawn.

Linear's extract_images answered two pictures. The service kept the first as a file and left the 6.4 MB one out, as Not kept; the model saw both. The row keeps main's line and gains the message box's chips under it, visible whether the row is open or closed. On main today this row's body is a wall of base64.

The same row, opened

The stored output now names the picture by id, type, size and dimensions. No bytes are in the message log, the stream, or the row's JSON.

A tool's picture in the lightbox

A chip opens the same viewer over the call's kept pictures, named after the remote tool.

Loading: the call still runs

While show_image runs, the service is reading the file from the sandbox, and the picture's shape is not known yet. The transcript holds its place at 480 by 300, with the spinner and the path it is showing.

Loading: the bytes are being read

Once the call has answered, the picture's size is known, so the quiet box takes its exact shape and the turn does not jump when it lands. The chips wait the same way. This is plan-media's pending state (318's plan-image-pending), lifted into the shared StoredImage.

Failure: the read did not answer

The Inbox's line, “The image could not be read.”, with Retry, inside the picture's own box. A chip that failed shows the image-off glyph.

Failure: the file is gone

The conversation's files were purged, or this reader cannot reach the agent. The picture draws as its caption, marked “not available”, as a plan picture does.

Failure: the call was refused

Over 3 MB, not a PNG, JPEG or WebP, or a path outside the checkout: the call fails with one sentence the model can act on, and its row stays a row, open here, with its error in red.

A markdown image in a reply is never fetched

![alt](path) to a sandbox file, or to any URL, draws as a link with the image-off glyph, never as an image element. On main, Streamdown's hardening draws a relative one as a grey “[Image blocked: …]” pill and an https one as nothing.

A 390-wide phone screenshot draws at its own size and at most 420 tall, never stretched to the column.

Decisions for Dean

  1. Sources in v1. Recommended show_image from the sandbox, and MCP image results kept automatically. Later: the agent's own read_file of an image, the planning conversation's pictures on the Call tab, generated images, Mac screenshots.
  2. How an agent shows one. Recommended an explicit show_image(path, caption) tool. The alternatives were capturing every image the agent reads, or resolving ![](path) in replies from the sandbox.
  3. Storage. Recommended a conversation_attachment table beside plan_attachment and inbox_attachment, sharing 318's intake, serving and window cache. The alternatives were one polymorphic table, or Vercel Blob.
  4. How the transcript names a picture. Recommended {id, mediaType, width, height, byteCount} in the stored output, with no bytes and no URL.
  5. Limits. Approved, then revised after benchmarking 4 MB per picture (raw bytes, under Vercel's 4.5 MB response), a 200 MB budget per conversation in bytes rather than a count, and deduplication by hash. Anything over the limits is recorded as “Not kept”. Both are one constant each in CONVERSATION_PICTURE_BOUNDS.
  6. Does the model see what it showed? Recommended no: show_image answers the model in words. It reads its own file with read_file when it wants to look.
  7. Where pictures draw. Recommended a shown picture inline, out of the finished turn's fold. MCP pictures as chips under their row, open or closed. Both open the shared viewer.
  8. Who sees them. Recommended whoever can read the agent, checked on every read. Never in traces, counted events or fixtures beyond ids. Covered by a PRIVACY.md paragraph.
  9. Markdown images in replies. Recommended never fetched, drawn as a link with the image-off glyph.
  10. Add to plan. Recommended copy the bytes into the plan and write the line at the end of the plan as your edit, or at the caret if the plan editor is open.
  11. A browser in the sandbox. In progress not in v1, where the instructions tell the agent how to install Playwright. Worker 349 (agent capability gaps) is now building it into the sandbox.
  12. Order. Recommended keep MCP pictures by reference first, independent of 318's PRs. Drawing them shares 318's PR 3.
  13. Several pictures in a row. Recommended show_image takes 1 to 20 images, and calls in one step with nothing between them draw as one set. Two or three pictures draw as one justified row; four or more draw as wrapping thumbnails, six shown and “+N” on the sixth. The viewer walks the whole set.
